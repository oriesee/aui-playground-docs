Part 3

Constraints

Defining the truths that control tool execution

The Constraints tab is where you define the "truths" that control tool execution. These are structured WHEN/THEN rules enforced at the architectural level.

Constraint Types

TypePurposeExample
Policy ConstraintsBusiness rules that block or modify behavior"Block disputes for transactions older than 60 days"
Authentication ConstraintsRequire identity verification"Require phone verification before changing email"
Confirmation ConstraintsRequire explicit user consent"Ask for confirmation before processing refund"

Building Constraint Rules

Each Policy Constraint follows a WHEN/THEN structure with powerful condition building, based on the current explicit state of the interaction.


WHEN ConditionsDescription
Existing parameters in conversationChecks whether specific parameters have already been set in the ongoing conversation context. 
Extracted parameters in current interactionIdentifies parameters that have been captured or recognized during the current user interaction. 
Missing parameters in conversationDetects if certain required parameters are absent in the conversation data. 
Entity parameters referenced in current interactionDetermines whether any entity-type parameters are mentioned or used within the current exchange.
User's questionAnalyzes the content or intent of the user's latest question or message.
User profile parametersEvaluates data stored in the user's profile, such as preferences or account status
Conversation createdTriggers conditions based on the creation or start of a new conversation session.
Current URLAssesses the present URL context, useful if the assistant is embedded on different pages.
Tool required/optional parameters filled status

Checks if all required (and optionally, additional) parameters for a given tool or integration have been provided.


Condition Combinators:

  • AND: All conditions must be true
  • OR: Any condition can be true
  • AND NOT: First condition true, second must be false

THEN Actions (ordered by strictness):

ActionDescription
BlockCompletely prevents the tool from executing. The agent will not proceed with the action and will inform the user that the request cannot be fulfilled.
Block and activate another toolPrevents the current tool from executing but immediately redirects the conversation to a different tool. Use this for graceful handling where instead of just stopping, you route the user to an appropriate alternative (e.g., block a premium feature for free users and activate the "Upgrade Account" tool instead).
Block and activate another APIPrevents the current tool from executing but calls a specific API integration. Use this when the block requires triggering a backend action or fetching specific data as part of the blocking flow (e.g., block a transaction and call a fraud-logging API)
Ask a questionPauses execution to ask the user for additional information or clarification before proceeding. Unlike confirmation (which asks for consent), this gathers missing information needed to evaluate whether to continue (e.g., "Which card would you like to use for this transaction?").
Add text guidelinesInjects additional instructions into the agent's context for this interaction without blocking execution. Use this to modify how the agent responds or behaves based on specific conditions (e.g., when a user mentions competitors, add guidelines to focus on your product's unique value).
Activate another toolRedirects the conversation to a different tool without blocking. This is a handoff that allows the flow to continue through a more appropriate tool based on the detected conditions (e.g., if the user asks about policies mid-search, activate the "Policies" tool).
Activate another APICalls an additional API integration as part of the current flow. Use this for enrichment or fetching supplementary data based on conditions (e.g., when a high-value customer is detected, call the loyalty-points API to include rewards information).
Activate a sub-toolActivates a nested tool that operates within the scope of the current tool. Sub-tools allow modular composition—breaking complex tool logic into reusable components that can be triggered conditionally (e.g., within a "Car Search" tool, activate a "Financing Calculator" sub-tool when the user mentions budget constraints).

Advanced

Constraints are evaluated based on state, and related entities. State is formed multiple times within an interaction, per entity, triggering all relevant constraints per state.

Example Constraint

Rule: "When a user references a vehicle trim and asks about policies, activate the Policies sub-tool and add guidelines."

WHEN   Entity parameters referenced in current interaction     → Cars → Vehicle trim → Has any value AND   User's question → Is about → "policies" THEN   Activate a sub-tool → Policies AND   Add text guidelines → [Custom guidelines for policy responses]

Confirmation Constraints

When enabled, the agent will:

  1. Summarize the action about to be taken
  2. Present a confirmation button to the user
  3. Only proceed after explicit confirmation
Example

Before submitting a dispute, the agent shows: "Just to confirm, you'd like to dispute the $199.99 Best Buy transaction from January 23, 2026, on your Visa card ending in 4821 as an unauthorized charge. Should I go ahead and submit this dispute for you?"
